# GarageBot logic: contracts

This file lists every function of the proven core (`logic/src/fns/*.rs`), what it
must do, and which other functions it calls. It also lists the top-level
properties (`logic/src/props.rs`) that are proven from these contracts alone.

The unproven remainder is in `TRUSTED.md`.

## How the proof is put together

- Every function `f` has one contract: **its result equals `spec_f(args)`**, the
  executable specification in `logic/src/spec.rs`. No function has a
  precondition: each is total, and must not panic, overflow or index out of
  range for any input of its types. The Kani harness `contract_f` proves this
  for the body.
- When `contract_f` checks a body, every callee listed for `f`, and that
  callee's specification, are replaced by one stand-in that returns any value
  but repeats itself for equal arguments ("Changes", point 1). A body may call
  only the callees listed, and nothing from `spec.rs` (the firmware build does
  not compile `spec.rs`).
- The top-level properties replace the functions they call by their
  specifications (`#[kani::stub(step, spec_step)]`). They do not depend on any
  body. They hold for the finished firmware once every `contract_*` proof passes.
- `cache.py` keeps the bookkeeping: `passing` counts harnesses whose proof
  passes; `sound` counts those whose stubbed callees are proven too. With no
  bodies written, the 69 `contract_*` harnesses cannot pass; the 22 properties
  and 5 lemmas do.
- Run Kani through `proofq` (`~/proofq/README.md`). `cache.py run` does so. Run
  one `cache.py` at a time: a second job for the same folder cancels the first.
- **The function list, the callee lists and the readiness of each proof are in
  "Changes" at the end (2026-11-22: 69 functions).** The tables in "Functions"
  below describe results and are kept for that; their callee columns and the
  45-function split are out of date.
- The harnesses are generated by `tools/gen_stubs.py`. It only overwrites a
  file whose body is still the stub.

## What was changed to end the timeouts

Three of the 17 properties ran out of time (1200 s): `prop_anchor_is_sound`,
`prop_stale_never_executes` and `prop_open_alert_schedule`. The cause was the
same in all three. Kani hands the proof to a SAT solver, and a SAT solver cannot
relate two 64-bit multiplications or divisions by a constant to each other. The
old harnesses wrote real time in milliseconds and converted with `* 1000`,
`/ 1000` and `/ 60_000`, next to the same conversions inside the contracts.

Nothing was narrowed. Two things were restated.

### Ghost time is split (anchor and stale properties)

True (real-world) time appears only in the harnesses, as a ghost value. It is
now written as a pair (whole seconds `s`, remainder `r < 1000`) standing for
`s * 1000 + r` ms. Each old statement about milliseconds has an exact
counterpart on pairs, and every true time below 2^60 ms is still covered:

| Old statement (ms) | New statement (pairs) |
|---|---|
| A1: `rt_req < (D + 1) * 1000` | `req_s <= D` |
| A2: `t_req_ms <= (rt_req - rt_boot) + 1000`, with `rt_boot <= rt_req` | `up = (up_s, up_r)` is the true time from boot to the request, `up <= req` pairwise; `(t_req_ms / 1000, t_req_ms % 1000) <= (up_s + 1, up_r)` pairwise |
| proved: `rt_req < unix_s * 1000` | `req_s < unix_s` |
| proved: `rt_boot < b * 1000` | `boot_s < b`, where `boot_s = req_s - up_s` minus 1 if `req_r < up_r` |
| anchor sound: `rt_k < unix_s * 1000` | `k_s < unix_s` |
| A3: `rt_now - rt_k <= (now - mono_ms) + 1000` | `el <= (now - mono_ms) + 1000`, where `el` is the true ms since the anchor |
| proved: `rt_now < (d + STALE_AFTER_S) * 1000` | `k_s + (k_r + el) / 1000 < d + STALE_AFTER_S` |
| proved: `d * 1000 > rt_boot` | `d > boot_s` |

"Pairwise" is the usual order on (seconds, remainder): the first differs, or
the first is equal and the remainders compare. The stale property first proves
`el <= ANCHOR_MAX_AGE_MS + 1000` whenever the relay is pressed, so the one
division left in the harness is on a number below 302_000.

### Minutes are opaque in the schedule property

`prop_open_alert_schedule` used to assert `minutes == (now - open_since) / 60_000`.
It now asserts `minutes == spec_whole_minutes(now - open_since)` with
`spec_whole_minutes` replaced by a function about which the solver knows
nothing. This proves the alert carries the minutes of exactly that duration,
for all u64 durations, whatever the minutes function is. The step from there to
"whole minutes" is the one-line definition of `spec_whole_minutes` in
`spec.rs` (`elapsed_ms / 1000 / 60`), read by a person (entry in `TRUSTED.md`). `prop_open_alert_minutes`
checks seven concrete durations with the real function.

## Arithmetic the solver cannot do

Kani hands each proof to a SAT solver (cadical; kissat and minisat are the only
others installed). A SAT solver cannot show that two separate 64-bit divisions
or multiplications by a constant give the same result, although they obviously
do. A `contract_f` proof compares the body with `spec_f`, and a caller's proof
compares the callee's contract with the caller's spec, so this situation comes
up whenever both sides divide. Measured on eE, two copies of the same expression
on one `u64`, proven equal:

| Expression | Time |
|---|---|
| `x / 10` and `x % 10` | 47 s |
| `x / 1000` | 42 s |
| `(x + 3000) / 1000 / 6` | 186 s |
| `x / 1000 / 60` | 379 s |
| `x / 6_000` | 345 s |
| `x / 60_000` | no result in 600 s |
| 20 chained `/ 10` (decimal digits of a `u64`) | no result in 900 s |
| 7 chained `/ 1000` | no result in 900 s |
| `q * 60_000 <= x` for a quotient `q` | no result in 600 s |

Three things follow from this.

**1. Minutes and tenths are two-stage divisions.** `spec_whole_minutes` is
`e / 1000 / 60` and `spec_tenths` is `(e + 3000) / 1000 / 6`. These are the same
numbers as `/ 60_000` and `/ 6_000`. A body should divide in the same two
stages; `contract_whole_minutes` and `contract_tenths_of_minute` need
`--timeout 900`.

**2. Decimal digits go through `div10` and `dec`.** `div10` is one step and is
proven against real division (one pair of dividers). `dec` is proven with
`spec_div10` swapped for a stand-in (`opaque::div10_opaque` in `spec.rs`): a
function that returns any quotient and digit having the facts in
`opaque::div10_facts`, and the same answer for the same argument along the
chain `v, v/10, v/100, ...`. So `contract_dec` shows: for every function with
those facts, the body yields what `spec_dec` yields. `lemma_div10_facts` proves
that real division has those facts. Consequence for the body of `dec`: every
quotient and digit must come from a call to `div10`, on `v` and then on the
quotient of the previous call. A `/` or `%` written in `dec` makes its proof
fail.

Everything above `dec` (`text_push_u64`, `text_push_i64`, `text_push_padded`
and the six `render_*` functions) has `spec_dec` swapped for
`opaque::dec_opaque` in its harness: any 20 bytes and any start index below 20,
the same ones for the same number. Those proofs then hold whatever the digits
are. `lemma_dec_index` proves that the real `spec_dec` never panics and returns
an index below 20. Consequence for those bodies: digits must come from `dec`
(or from a callee that uses it), never from their own arithmetic. The stand-in
remembers up to 12 different numbers per proof.

**3. Top-level properties state real time in (seconds, remainder)** and treat
minutes as opaque (previous section).

Why a stand-in is sound: a stand-in may return more values than the real
function ever does. A proof that holds for all of them holds for the real one,
provided the real one has every fact the stand-in assumes. Those facts are
proven by the two lemma harnesses. The step "proven for every such function,
therefore for this one" is made by a person, not by Kani (entry in `TRUSTED.md`).

`door_tick`, `step` and `bot_step` have `spec_whole_minutes` and `spec_tenths`
on both sides of their contract proof (through `spec_door`). Their trial proofs ran out of time (1500 s). They need the same stand-in treatment as
`prop_open_alert_schedule`; this is not done yet (next section).

### Loop limits

Each harness with a loop has `#[kani::unwind(N)]` (table `UNWIND` in
`tools/gen_stubs.py`). Kani fails a proof when a loop can run longer than `N`,
so a limit that is too small cannot make a wrong proof pass. A body author may
change this one number in the harness of their own function. Nothing else in a
harness may be changed.

## Slice length bounds

A `contract_f` harness for a function with a slice argument checks slices up to
the bound in the tables. The contract itself has no length limit, and callers
that use the contract assume it for any length. Lengths above the bound are
therefore not machine-checked. Longest lengths that actually occur:
`text_push` about 62 (the longest message literal) or the length of `notify` and `version`, `text_push_json` up to `TEXT_CAP`,
`parse_u64`, `parse_i64`, `classify_key`, `name_from` up to `TMP_CAP` (64),
`parse_command` up to `CMD_TEXT_CAP` (64), `notify`, `version`, `msg` and
`date_hdr` as long as the shell passes. This gap is an entry in `TRUSTED.md`.
Raising a bound means editing `tools/gen_stubs.py` and regenerating the harness.
None of the top-level properties uses a slice function.

#### 1. The form of the proofs changed

The contract of every function is unchanged: **the result equals
`spec_f(args)`, for every input, with no panic.** What changed is how Kani is
asked to check it.

Before: `#[kani::ensures]` on the function, `#[kani::proof_for_contract]` on
the harness, `#[kani::stub_verified]` for callees. Measured: in that mode Kani
needs about 2 million clauses for every `Msg` or `Op` value a function builds,
and runs out of memory on `Text` arguments. `pick_op` came to 47 million
clauses; the same check as a plain proof is 81 thousand. This, and Kani's
extra reachability checks (point 5), were the cause of all 20 "not ready"
harnesses and of `on_update` running out of memory with a real body.

Now:

- `contract_f` is a plain `#[kani::proof]`: any arguments, then
  `assert!(f(args) == spec_f(args))`. Functions that return a `Text` compare
  with `opaque::gb_text_eq`, which `lemma_text_eq` proves to be the same as `==`.
- A function with callees: every callee `c` **and** `spec_c` are replaced by
  the same stand-in (`#[kani::stub(c, ..)]`, `#[kani::stub(spec_c, ..)]`; the
  stand-ins are in `spec.rs`, `mod opaque`). The harness evaluates
  `spec_f(args)` first while the stand-ins record, then `f(args)` while they
  replay. A stand-in returns any value the first time it sees an argument and
  the same value when it sees an equal argument again. So the proof shows:
  whatever the callees return, `f` combines their answers the way `spec_f`
  does. Together with each callee's own proof (`c` equals `spec_c`) this gives
  `f` equals `spec_f`.
- The top-level properties replace each function they call by its
  specification: `#[kani::stub(step, spec_step)]` and so on. They do not
  depend on any body.
- No function has a Kani contract attribute any more. `cache.py` reads the
  callees of a harness from its `#[kani::stub(c, ..)]` lines.

What this asks of a body, beyond what was asked before:

1. Call only the listed callees, and call each with the arguments the
   specification gives to that callee's specification. A call with other
   arguments gets an unknown answer and the proof fails.
2. Stand-ins with a `Text` argument (`text_push`, `text_push_u64`,
   `text_push_i64`, `text_push_pad6`, `text_push_json`, `push_mention` and the
   `render_*` callees) replay in order: the j-th call of the body is matched
   with the j-th call of the specification. Build texts in the order the
   specification does.
3. A stand-in remembers 4 calls (`text_push` 12, `text_push_u64` 8,
   `json_escape` 8; table `SLOTS` in `tools/gen_stubs.py`). No function needs
   more today.
4. A logic function must be pure. `cache.py` refuses `static`, `unsafe`,
   `Atomic*`, `Cell`, `RefCell`, `UnsafeCell` and `extern` in `fns/*.rs`. The
   old contract mode checked writes to statics itself; this textual check
   replaces that and is listed in `TRUSTED.md` (T11).

Three facts a stand-in may assume, each proven by a lemma: the start index of
`dec` is below 20 (`lemma_dec_index`), the length from `json_escape` is at most
6 (`lemma_json_escape_len`), and `parse_u64` of at most 18 bytes is below
10^18 (`lemma_parse_u64_18`). `dec` keeps its own `div10` stand-in as before.

Slice length bounds in the harnesses are unchanged (section "Slice length
bounds"). A slice longer than a stand-in's key (96 bytes; 512 for
`text_push_json`) is never replayed, which can only make a proof fail.

  yes. That only decides whether the report says "holds" or "unreachable". It
  took most of the time and memory: `on_update` went from out of memory at
  4 GB to 13 s and 0.7 GB. The `kani::cover!` checks of the properties are
  separate and still run.
- Loop limits by name (`--unwindset`): `memcmp` 514, `gb_text_eq` 34,
  `gb_sk_fill` 514, `gb_words_eq` 34. These are the byte comparison behind
  `==` and the stand-ins' key code. A limit that is too small fails the proof.
- `#![recursion_limit = "512"]` in `lib.rs`: the harness of `step` carries 16
  stub attributes.
